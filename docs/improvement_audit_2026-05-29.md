# Wrist Assistant Integration — Improvement Synthesis

## Executive summary

The single biggest speed win is **decoupling camera-snapshot capture from the doorbell push** (`__init__.py:280-301`): today a slow RTSP camera can sit up to 5s on the critical path before the alert even reaches the relay; bounding capture to ~0.8-1.5s with the existing on-demand `camera_entity_id` fallback turns a multi-second doorbell alert into a sub-second one with no visual regression. The single biggest wow bet is **a signed first-frame returned from `op=stream_open`** (`wa_v2_views.py:1717`), which collapses the two-round-trip camera open so a real pixel paints after one RTT — directly attacking the most visibly "slow" watch interaction. Most of the per-event-loop micro-optimizations (delta lazy-build, deque double-scan, gzip offload, secret/JSON dedup) are real but were uniformly verified as sub-millisecond on a path that then blocks for seconds — they are tidy-ups, not felt speed. The highest-leverage low-effort items are timeout/parallelism fixes on the relay and setup paths, plus three trivial manifest keys. Wow value concentrates in features whose hard work lives in the **app repo, not this one** — server-side slices are genuinely small.

## Speed wins

Ordered by impact-to-effort. Latency wins were heavily discounted where verification found the saving is sub-ms on a path that blocks for seconds.

1. **Bound the inline snapshot capture on camera pushes** — cap `NOTIF_SNAPSHOT_CAPTURE_TIMEOUT` at ~0.8-1.5s (down from 5s) and fall through to the existing `camera_entity_id` on-demand fetch on timeout, instead of awaiting capture before the relay loop. *Why:* a laggy/RTSP doorbell currently adds up to 5s of pure latency before the push leaves the box; bounding it makes the 95% fast-camera path keep its frozen frame and the slow path degrade gracefully. *Latency:* worst-case alert drops from capture(≤5s)+RTT to ~one RTT (sub-second to low-seconds). *Files:* `homeassistant-wrist-assistant/custom_components/wrist_assistant/__init__.py:280-301,344-373`, `camera_stream.py:556,579-599`. *Effort:* small (timeout/task plumbing + cancel handling). *Risk:* medium (do NOT ship pure "fire text first" — it loses the frozen-frame moment users expect from a doorbell). Server-side only.

2. **Parallelize the advanced setup sweep** — run the five independent probes (`probeClockSkew`, `probeIPhonePushReady`, `probeFallbackURLReachable`, `probeAppUpToDate`, `probeWidgetCredentialsHealthy`) with `async let` / TaskGroup instead of serial awaits. *Why:* they share no data; serially one wedged probe (e.g. App Store lookup at its 10s timeout) blocks every probe behind it, so worst case is ~45s. Parallel caps total wait at the single slowest probe. *Latency:* shaves ~2-3s off the wizard's first all-green flash on remote/cellular; the pathological case drops from ~45s to one timeout. One-time per session (gated by `advancedChecksRan`). *Files:* `wrist-assistant-app/WristAssistant/Services/SetupHealth.swift:1595-1603,2906-2938,2533-2698`. *Effort:* small. *Risk:* low (verify Swift 6 strict-concurrency with `check-build.sh`; all mutated state is @MainActor so no data races). iOS app work.

3. **Skip the redundant `/version` re-probe on the iPhone provisioning step** — add `skipReachabilityProbe: Bool = false` to `verifyIdentity`; the SetupHealth cascade passes `true` because `integrationVersion` proved `/version` seconds earlier. *Why:* the iPhone step pays an extra serial `/version` RTT (and a third in the `.stale` auto-rotate branch) to re-establish reachability the cascade already proved; the iPhone step gates the watch + push steps. *Latency:* removes 1-2 serial `/version` RTTs (~300ms-1s each on remote). *Gotcha (load-bearing):* gate `skipReachabilityProbe=true` on `stepStatus[.integrationVersion] == .passed || integrationVersionIsSoftUpdate`, NOT on `userSkippedSteps.contains(.integrationVersion)` — a user-skipped version step proved nothing, and skipping the probe would misread a captive-portal 401 as `.stale` and falsely trigger auto-rotate. *Files:* `wrist-assistant-app/WristAssistant/Services/IPhoneIdentityService.swift:261-326,373`, `SetupHealth.swift:1405-1478,2152-2156,2189`. *Effort:* small. *Risk:* low. iOS app work.

4. **Eagerly warm the relay_token at push-token registration** — in `_op_notifications_register`, fire a shielded, time-bounded `async_create_background_task(client._register_device(...))` after `store.register()` so the relay_token is cached before the first real push. *Why:* `send_push` registers lazily, so the very first push (the wizard test, and the first organic alert after any token rotation) pays 2 serial relay RTTs. *Latency:* removes one of two serial relay RTTs (~100-400ms) for delayed/organic pushes. *Caveat (verified):* this does NOT speed up an immediate test push fired seconds after register — the background task hasn't completed, so the synchronous test still pays the same single register. Frame the win as later organic pushes, not "fixes the slow test." Guard: skip if `relay_token` already set; warm only the platform being registered. *Files:* `homeassistant-wrist-assistant/.../apns_client.py:56-69,135-167`, `wa_v2_views.py:1455-1537`. *Effort:* small. *Risk:* low. Server-side only; best paired with the relay timeout (Reliability #1).

5. **Lower the `camera_batch` per-camera grab timeout** — add `CAMERA_BATCH_TIMEOUT` (~2.5s) and use it at `wa_v2_views.py:1621`, leaving single-camera `_op_snapshot` at 5s. *Why:* a grid returns as one signed body, so the slowest/offline tile's full 5s timeout gates all 8 cameras even if 7 returned in 300ms. *Latency:* caps worst-case grid latency at ~2.5s instead of 5s; healthy grids unchanged. *Do NOT* skip gzip (measured to claw back the full +33% base64 expansion at ~8ms) and do NOT attempt chunked/multipart streaming (new wire protocol across both repos). *Files:* `homeassistant-wrist-assistant/.../wa_v2_views.py:1585,1621,1633`, `camera_stream.py`. *Effort:* trivial (one-liner). *Risk:* low. Server-side only.

- **Gather four cold-start store loads** (`__init__.py:549-558`) — a few ms once per restart; the real cold-start cost is `_install_bundled_blueprints`. trivial/low.

## Reliability fixes

1. **Add an explicit timeout to relay HTTP calls** — pass `aiohttp.ClientTimeout(total=8-12, sock_connect=3)` to `_post_json` AND widen the except to catch the bare `asyncio.TimeoutError` (the total-timeout path raises it, and it is NOT an `aiohttp.ClientError` — the current `except (ClientError, ValueError)` misses it). Requires `import asyncio` in `apns_client.py`. *Why:* a hung relay (TCP up, no response — common with Cloudflare cold paths) currently blocks the awaiting `send_notification` service / v2 op up to aiohttp's ~5-min default — functionally a hang on every push, single or broadcast. Converts an unhandled hang into a clean per-watch `connection_error` so dead-token/retry logic and the on-demand image fallback proceed. *Latency:* bounds worst-case delivery (~10s vs up to ~300s); not a happy-path win. *Files:* `homeassistant-wrist-assistant/.../apns_client.py:169-176`, `__init__.py:756-767,848-859`. *Effort:* trivial. *Risk:* low. Server-side only. **This is the single highest-confidence reliability lever and pairs with every push-path item below.**

2. **Add three manifest keys** — `"single_config_entry": true`, `"integration_type": "service"`, `"loggers": ["PIL"]`. *Why:* the entire codebase assumes one global entry (`hass.data[DOMAIN] = runtime_data` is a bare overwrite at `__init__.py:583`), but the manifest doesn't enforce it — a second entry would silently corrupt both coordinators. `integration_type` is a straight correctness fix (it's a service, not a hub); `loggers` lets users set Pillow log level. *Files:* `homeassistant-wrist-assistant/.../manifest.json:1-13`, `config_flow.py:17`, `__init__.py:583,585-627`. *Effort:* trivial (keep keys alphabetically sorted for hassfest). *Risk:* low, metadata-only. Server-side only.

3. **Broaden diagnostics + add a public coordinator snapshot accessor** — add `coordinator.diagnostics_snapshot()` so diagnostics stop indexing private fields (`_sessions`, `_cursor`, `_generation`, `_events`, `all_tokens`); add paired-device count + per-watch algo/device_kind/app_version (never secrets), nonce-cache occupancy + `WA_ACCEPTED_PROTOCOL_VERSIONS`, stream-token store size, and the relay base URL; wrap with `async_redact_data`. *Why:* a single diagnostics download can't currently distinguish a pairing problem from a sync or push problem — the top support cases. Support ergonomics, not a runtime fix. *Files:* `homeassistant-wrist-assistant/.../diagnostics.py:21-56`. *Effort:* small (~4 new public accessors to add — heavier end of small). *Risk:* low. Server-side only.

4. **Fix the snapshot-store eviction policy** — change `put()`'s cap-eviction from `popitem(last=False)` (oldest-inserted) to evicting the soonest-`expires_at` entry, so a still-live token never loses to an older/expired one during a doorbell burst; optionally bump `_MAX_ENTRIES` 32→64 (~16MB) as belt-and-suspenders. *Why:* >32 camera pushes in the 600s window currently evict still-valid tokens, 404-ing earlier notifications opened from Notification Center. *Do NOT* attempt the `/live` cold-miss re-capture (the token URL carries no camera — that fallback is the client using `camera_entity_id`, an app concern). Add a unit test (none covers this store today). *Files:* `homeassistant-wrist-assistant/.../notification_snapshot.py:45-99`, `wa_v2_views.py:1962-1976`. *Effort:* small. *Risk:* low. Server-side only. Narrow real-world impact.

The following were verified as hardening with no current user impact — do the safe half only:

- **Content-hash guard on `_install_bundled_blueprints`** — skip the `write_text` + cross-component cache reset when the bundled file is byte-identical (rewrites every restart today). Upgrade the swallowed debug log at :908 to `warning` so a future core-API break is visible; do NOT add an issue_registry repair (nags ~100 users over a benign internal detail). `__init__.py:675,866-911`. small/low.
- **Add a no-op `async_migrate_entry` scaffold** — cheap insurance before the planned v1-removal release needs to restructure `entry.data`/stores. Do NOT move `_clear_stale_statistic_units_once` into it (it intentionally retries across restarts and needs entities forwarded). `config_flow.py:13`, `__init__.py:416-448,467-542`. The scaffold is the only worthwhile piece.
- **One-line comment at `async_unload_entry`** documenting that the `_views_registered` guard is intentionally not cleared (`register_view` is one-way). **REJECT** removing/gating the v1 routes — `WA_ACCEPTED_PROTOCOL_VERSIONS={2}` gates HMAC v2 signatures, NOT the separate bearer-authed v1 URLs; v1 clients can still exist and `V1_REMOVAL.md`'s preconditions are not met. `__init__.py:585-627,783-792`.
- **Per-watch `asyncio.gather` on the broadcast loop** — correct and safe (`return_exceptions=True`), but payoff is marginal: realistic N is 1-3 and it does nothing at N=1 (the test-push path). Bundle it with the timeout fix as a robustness nicety, not a headline speed item. `__init__.py:344-398`.

## Wow-factor bets

Ordered by wow-to-effort. **Critical framing:** the server-side (this repo) slice of every wow item is small; the bulk of the delight — and the effort — lives in the **app repo** (`wrist-assistant-app`). Server-only vs. app-work is flagged on each.

1. **Signed first-frame from `op=stream_open`** *(server slice small; needs app work)* — have `stream_open` optionally capture-and-return a single signed first-frame JPEG (best-effort, ~1.5s timeout, complication-tier size) alongside the token+URL; the watch paints it immediately, hiding the second round trip. *Why it's wow:* the camera open is the most visibly slow watch interaction; a real pixel after one RTT feels instant. *Quantified:* ~20-40% perceived TTFP improvement (NOT 50% — the cold `async_get_image` grab still dominates and is heavily camera-dependent). *Server (this repo):* `wa_v2_views.py:1717,1902-1938`, `camera_stream.py:363-389` — gate behind `"first_frame": true`, best-effort with a *tight* timeout so a slow camera never stalls the handshake. *App:* add the request flag and learn to paint the base64 frame before the MJPEG GET connects. *Effort:* medium. *Risk:* medium (binary-in-JSON inflates the response; tighten the timeout). This is the top wow bet because it doubles as the project's #1 priority (speed). *(The "prefetch first frame onto the StreamTokenEntry" variant at `wa_stream_tokens.py:38` is the same idea with a smaller, RTT-only win — fold it in if pursuing this.)*

2. **Haptic-coded alerts** *(server slice trivial; the wow is app-side)* — pass an optional `haptic` field through `extra_data` exactly like `sound` today; the watch maps it to a distinct `WKInterfaceDevice.play(...)` pattern. *Why it's wow:* the user learns "the language of their wrist" — a double-tap means leak, a long buzz means alarm — and triages without looking. *Server (this repo):* either ship it as a documented `data: { haptic: "leak" }` key (zero integration code, works today) or promote to a first-class field (`vol.Optional('haptic'): cv.string`, hoist at `__init__.py:752`, `services.yaml` selector + blueprint entry next to Sound — recommended for discoverability). `__init__.py:309-361`, `services.yaml:169-187`, `apns_client.py:71-82`, `blueprints/script/watch_notification.yaml:223-236`. *High-leverage move:* auto-derive haptic from priority level (passive→light, active→standard, time-sensitive→double, critical→strong-repeated) so users get distinct taps with zero config — pure-manual config will see low adoption. *App caveat to verify:* in "mirror" delivery mode a custom `WKHaptic` likely can't fire — scope the claim to direct/Reliable delivery. *Effort:* small (server); app work is the bulk. *Risk:* low.

3. **Voice-to-action via local Assist** *(text path needs ZERO server code; the wow is app-side)* — "raise wrist, speak, house responds." *Verified:* the marquee path needs no new op — the app transcribes locally and sends the existing `{op:"service", domain:"conversation", service:"process", service_data:{text, agent_id:"homeassistant"}, return_response:true}`, then speaks `response.response.speech.plain.speech` via the existing watch TTS. Do NOT add `op=assist` for the text path (it duplicates `op=service`). *Server (this repo):* nothing for the text path; only a raw-audio-over-the-wire bridge (uploaded clip → STT → conversation) is a small server task, and it's the lower-value half (on-device dictation is already good and avoids the 100KB upload cap). *Files:* `wa_v2_views.py:564-625,1094-1112,1268-1287,1540-1584`. *Caveat:* `conversation.process` exposes the user's full Assist agent including any LLM `agent_id` — consider pinning it. *Effort:* small (server, ~0 for text path); app work dominates. *Risk:* low (reuses the audited generic service op). Ship the text path first; defer the audio bridge.

4. **"Leaving home" proactive checklist push** *(server slice small; needs a blueprint + app rendering)* — on last-person→`not_home`, send ONE actionable push: "Garage open, back door unlocked, 6 lights on" with one-tap fix buttons. *Why it's wow:* the user shuts the house from the driveway without remembering to check. *Server (this repo):* a new `wrist_assistant.send_leaving_home_summary` service that reuses `_compute_info_summary`'s existing open-door/lights-on filters (refactor the `device_class` filter into a shared helper to avoid drift) and calls `_deliver_push` with enriched actions, plus a bundled blueprint (trigger + zero-person condition live entirely in HA core). *Design up front:* the 4-button cap — prioritize garage_door > door > lock/window, collapse remaining lights into ONE button targeting a light group/script (per-row buttons can't express bulk). *Files:* `api.py:1071-1204,1109-1173`, `__init__.py:238-407`, `wa_v2_views.py:564-625`. *Effort:* medium. *Risk:* low. Prototype the button-prioritization UX first — that's where the wow lands or dies.

5. **One-tap multi-camera "security wall"** *(server slice small; grid/promotion is large app work)* — motion alert → glance → see every camera in the area at once, tap to promote one to live MJPEG. *Server (this repo):* add `area_id` per device to `camera_devices` (an `area_registry` walk — NOT already done; grouping is device_id-only today) and carry `area_camera_ids[]` in the camera-push `extra_data` so the watch fires one `camera_batch` without a round trip. `wa_v2_views.py:1585-1716`, `camera_devices.py:158-255`, `__init__.py:299-301`. *App (the delightful, large part):* grid layout, tile→stream promotion, live-refresh loop, optional complication tap. *Effort:* large (overall). *Risk:* low (additive). *Load caveat:* bound the wall to ≤4-6 tiles and slow its refresh — 8 parallel `async_get_image` on a motion storm is real load on the HA box. `MAX_BATCH_CAMERAS` already caps fan-out at 8.

6. **Live Activities on the wrist** *(spans THREE repos — integration, out-of-repo relay, app — large→XL, high risk)* — a self-updating Smart Stack card: "Alarm arming — 28s", "Dryer done in 4 min", garage closing. *Why it's the highest raw wow (score 8):* it's the marquee surface Apple built Live Activities for. *Reality check (verified):* the "only `push_type` wiring + a widget are new" framing is wrong. Hard parts that do NOT exist: (a) an APNs `liveactivity` push path in the **out-of-repo relay** incl. push-to-start + update-token lifecycle and the `.push-type.liveactivity` topic suffix; (b) a brand-new per-state-change APNs fan-out loop server-side (the foreground long-poll wake is NOT reusable for background updates); (c) the full ActivityKit widget + token registration in the app. *APNs constraint:* Live Activity updates are rate-budgeted and can be dropped — per-tick `cover.position 0→100` will NOT deliver. *Sharper cut:* ship ONE kind first (alarm-arming countdown), compute a local end-time the widget ticks down itself (2-3 pushes total, not one-per-state-change), and keep the camera snapshot in `ContentState` as the real differentiator. The relay change must be designed and verified in the worker repo before any of this ships. *Files (this repo's slice):* `apns_client.py:35-133`, `__init__.py:238-407`, `notifications.py:30-49`, `api.py:663-690`. *Effort:* large/XL. *Risk:* high. Defer until a single-kind prototype proves the APNs budget math.

## Recommended sequencing

Optimizing for fastest perceived-speed gains first, then reliability foundations, then wow:

1. **Relay HTTP timeout + `asyncio.TimeoutError` catch** (`apns_client.py:169-176`) — trivial, highest-confidence; unblocks and de-risks every push-path change that follows. Do this first.
2. **Bound the camera-snapshot capture timeout + on-demand fallback** (`__init__.py:280-301`) — the biggest felt speed win (sub-second doorbell alerts); naturally pairs with #1.
3. **Parallelize the advanced setup sweep** (`SetupHealth.swift:1595-1603`) — biggest visible setup-time drop; one-time but high-impact on first impressions.
4. **Three manifest keys** (`manifest.json`) — trivial reliability foundation, land alongside the Python changes.
5. **Skip the `/version` re-probe** (`IPhoneIdentityService.swift`) + **`CAMERA_BATCH_TIMEOUT`** (`wa_v2_views.py:1621`) + **eager relay-token warm** (`apns_client.py`) — the remaining small speed/RTT trims; batch them.
